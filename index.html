A team vault that can be sealed.

LinkPass is an enterprise password manager built around a HashiCorp-inspired seal / unseal lifecycle: AES-256-GCM at rest, a 12-word master phrase, mandatory TOTP, role-based access, quorum-controlled export, and a browser extension that only injects a credential after an admin approves the request. This page documents the build, the boundaries, and the evidence.

01

Context

Team credentials usually live in the worst place that works: a shared spreadsheet, a chat thread, or a note taped to a monitor. They are convenient until someone leaves, a laptop is lost, or an auditor asks who read the production database password last month.

Sharing has no perimeter

A password pasted into chat is copied into devices, backups, and notification previews. Revoking access means chasing every copy.

Access is not observable

A spreadsheet cannot show who revealed a secret, when, or from which address. Offboarding is a hope, not a control.

Consumer vaults do not fit teams

Personal password managers optimize for one person. They do not model teams, quorum approvals, or an administrator who can export the whole organization.

LinkPass’s design goal was to make the root of trust explicit. The vault starts sealed, the key exists only while the process is running, and the highest-risk operation — exporting every credential — requires more than one administrator. The rest of the system is organized around that decision.

02

What was built

LinkPass is a single-organization vault with a FastAPI backend and a dependency-free web client. The table is the functional inventory; the sections that follow cover the parts where the security model actually lives.

Functional inventory as observed in the reviewed source.

One organization, one vault

LinkPass is not a multi-tenant service. The deployment assumes one organization owns the server, the database, the TLS material, and the master phrase. That assumption is part of the security model, not a missing feature.

03

Architecture

The backend is an asynchronous FastAPI application. The web client is a vanilla JavaScript single-page app served as static files. SQLAlchemy is the only path to the store. The browser extension is a separate Manifest V3 package that talks to the same API with a stored token.

Why this shape

  • The vault is sealed before authorization. The seal middleware runs before route handlers, so a sealed process cannot serve vault data even to a valid token.
  • The key is not a file. The master key is derived at unseal and stored in module globals; a restart clears it and returns the process to the sealed state.
  • Export is treated as a separate risk. Reading one credential and exporting every credential are different operations, with different authorization requirements.
04

Seal / unseal lifecycle

The seal is the central design decision. On a fresh install, LinkPass generates a 12-word BIP-39 phrase, derives a 256-bit key with PBKDF2-HMAC-SHA256, and holds that key in memory. On the next process start, the key is gone. The vault is sealed until an operator supplies the phrase again.

State A

Sealed

The key is absent from memory. Every route outside the unseal allowlist returns 423 Locked.

POST /api/system/unseal
Phrase verified → ← Restart / seal
State B

Unsealed

The derived key lives in process memory. Authenticated routes can encrypt and decrypt vault records.

GET /api/system/status

Figure 2. The sealed / unsealed state machine. The phrase is the only input that moves the system from A to B.

  1. 1
    First boot creates the root of trust

    If no salt file exists, the server generates a 16-byte salt and a 128-bit BIP-39 mnemonic, derives the key, and prints the phrase once to the process output.

  2. 2
    The key is derived, not stored

    PBKDF2-HMAC-SHA256 with 600,000 iterations produces a 32-byte key. The salt is on disk; the key is only in memory.

  3. 3
    A restart re-seals the vault

    When the process stops, the key is lost. The next start serves 423 until an operator unseals it.

  4. 4
    The phrase is the recovery boundary

    There is no key escrow and no reset path. A lost phrase means the stored credentials cannot be decrypted.

  5. 5
    Legacy key files are removed

    On a fresh install, a previous .master_key file is deleted. The current design has no on-disk master key.

The availability trade-off is deliberate

A sealed vault is unavailable by design. An operator must hold the phrase and be available after a restart. This is the cost of removing a persistent key file; it is not an accident in the deployment.

05

Access & quorum

Authorization is role-based at the organization and team level, then narrowed by the visibility of each credential. The highest-risk operation is a full export, which adds a quorum requirement on top of the org-admin role.

Access tiers and the operations they unlock.
Role Scope Notable operations
org_admin Organization User management, audit log, extension approvals, full export with quorum PINs.
team_admin Own team Team membership and team-scoped credential sharing; no organization export.
member Own credentials and shared teams Create and reveal permitted credentials; no admin views.

Each credential carries a visibility value: private_to_owner, team_only, shared_with_specific_teams, or org_wide. A time-bound user share adds expires_at and clipboard_ttl_seconds; expired shares are filtered out when the vault list is built, not by a background cleanup job.

The export quorum

A full export is not a normal read. The API counts the organization admins, calculates a majority, and verifies a unique PIN for each supplied admin. Duplicate usernames are ignored. The export is then encrypted with a random one-time password and returned with that password.

Required admin PINs max(1, (org_admins + 1) // 2)

The encrypted blob is assembled as salt + nonce + ciphertext and encoded in base64. The one-time password is shown once; it is not stored. The export action itself is written to the audit log.

Quorum is an approval control, not key splitting

The PINs authorize the export; they do not reconstruct the vault key. An operator who already holds the master phrase and database access is outside this control. The quorum protects the normal application path, not a hostile administrator with host access.

06

Browser extension

The extension exists to avoid putting a password on the OS clipboard. It asks the server for access to the current site, waits for an admin decision, and injects the approved value directly into the page.

  1. 01Request

    The content script posts the target URL with its stored token.

  2. 02Review

    An admin sees the pending request and selects a credential.

  3. 03Approve

    The admin completes a 2FA step before the payload is pushed.

  4. 04Poll

    The service worker polls every two seconds for up to 60 seconds.

  5. 05Consume

    The payload is marked consumed; a second poll cannot replay it.

The four-layer injection defense

  • Closed shadow DOM. The “LinkPass” button is rendered inside a closed shadow root so page CSS and scripts cannot select or restyle it.
  • Attribute check. Before injection, the script confirms the target is still a password or text input.
  • Instant submission. The value is written to the field, input and change events are dispatched, and the closest form is submitted.
  • Auto-clear. The field is wiped 500 milliseconds after submission.
The injection surface is broader than the control

The extension declares <all_urls> and attaches to the first password field on every page. The closed shadow root protects the button, not the value after it enters the page. A page script can observe the field between injection and the 500 ms clear. This is a documented residual risk, not a solved problem.

The backend is complete: request, list, approve, reject, and one-shot poll. The web client’s sidebar exposes an “Extension Requests” link, but no render route is registered for it in the reviewed build. That makes the extension path partial in this repository, even though the API and extension package exist.

07

Security boundaries

Each row states the mechanism, then the boundary that a reader should not cross when interpreting it. The boundary is part of the claim.

Security controls and their stated boundaries.
Control Implementation Boundary
At-rest encryption AES-256-GCM with a 12-byte nonce per secret; the derived key lives in process memory. No HSM or KMS. A host-level memory compromise is outside the model.
Master phrase BIP-39 12 words (128-bit entropy), PBKDF2-HMAC-SHA256 at 600,000 iterations, 16-byte salt. The phrase is the root of trust. Loss is unrecoverable; there is no escrow.
Sealed state Global middleware returns 423 for every route outside the allowlist. Availability depends on a phrase holder being present after a restart.
Login Bcrypt hashes; three failures lock the account for 15 minutes; passwords rotate at 30 days. Lockout is application-level; it is not a network rate limit or WAF.
TOTP Mandatory enrollment in the login flow; secrets encrypted with the vault key; verification issues the JWT. If the vault is sealed, login cannot proceed; there is no separate recovery code path.
RBAC org_admin, team_admin, member; visibility per credential. No per-credential ACL beyond team and share scopes.
Quorum export Majority of org-admin PINs; encrypted one-time export; action audited. Authorizes the application path; does not stop a host-level administrator.
Audit Append-only rows with a 90-day retention purge on new log creation. Database-level, not WORM or an external SIEM sink.
License RS256 JWT with issuer LinkPass-KeyGen; missing or expired returns 402, invalid returns 403. If no public key is configured, the middleware bypasses the check (development mode).
Development secrets Compose ships a sample JWT secret; TLS certificates and a test license are in the repository. These are development artifacts. Replace them before any real deployment.
08

Findings

These are engineering findings from the build, not the results of an external security audit. Each one changed the implementation or the scope of what is claimed.

F-01

A persistent master key was a liability

SymptomThe original build kept a .master_key file beside the application.

ResolutionRemove the file, derive the key from the phrase at unseal, hold it only in memory, and delete the legacy file on a fresh install.

F-02

Restarts had to fail closed

SymptomA restart clears the in-memory key, so vault routes would fail unpredictably.

ResolutionAdd a global seal middleware with a small allowlist, a status endpoint, and an explicit 423 response.

F-03

Quorum needed a deterministic threshold

Symptom“A majority of admins” is ambiguous when admins are added or removed.

ResolutionCalculate max(1, (org_admins + 1) // 2) at request time and ignore duplicate usernames in the supplied PIN list.

F-04

Time-bound shares needed query-time filtering

SymptomA share that expired was still returned by a naive join.

ResolutionFilter expires_at > now when building the vault list and carry the per-share clipboard TTL to the client.

F-05

Extension payloads could be replayed

SymptomA poll that returned an approved payload could be repeated.

ResolutionMark the request consumed on the first successful poll; subsequent polls return the terminal status.

F-06

The approval UI did not ship with the API

SymptomThe sidebar links to #extension-requests, but no route renders that view.

ResolutionScope the extension as partial in this publication; the backend and MV3 package are present, the admin screen is not.

F-07

PostgreSQL was configured but not wired

SymptomCompose sets DATABASE_URL to PostgreSQL and starts a database service, while server/database.py hardcodes a SQLite URL.

ResolutionDocument the current runtime as SQLite and treat the PostgreSQL path as an unfinished migration, not a supported deployment claim.

F-08

Injection is inherently visible to the page

SymptomOnce the password is written into a DOM field, page scripts can read it, even if the overlay is isolated.

ResolutionReduce exposure with immediate submission and a 500 ms clear, and state the residual risk instead of claiming the clipboard was the only leak path.

09

Scope & limits

In scope

  • Single-organization team vault
  • AES-256-GCM at rest and in-memory key handling
  • Seal / unseal lifecycle and 423 gate
  • TOTP login, lockout, password rotation
  • RBAC, team and user sharing, audit
  • Quorum-controlled encrypted export
  • MV3 extension and injection API
  • Docker and standalone server packaging

Not claimed

  • High availability or multi-node clustering
  • HSM, KMS, or hardware-backed key storage
  • SSO, SCIM, or directory sync
  • Mobile applications
  • PostgreSQL runtime support
  • External penetration test or certification
  • Recovery of a lost master phrase

Limitations

  1. Phrase loss is permanent. There is no escrow, recovery code, or vendor reset. A lost phrase means the vault is unreadable.
  2. Restart equals downtime until unseal. The design trades availability for the removal of a persistent key.
  3. The key lives in process memory. A root-level memory compromise or core dump is outside the protection model.
  4. Audit retention is destructive by design. Logs older than 90 days are purged when a new entry is written; export them if you need a longer record.
  5. Clipboard clearing is best-effort. The client writes an empty string after the TTL; OS clipboard managers may retain history.
  6. Extension scope is broad. The manifest uses <all_urls> and attaches to the first password field; page scripts can observe post-injection values.
  7. License enforcement is conditional. With no public key configured, the middleware allows requests; this is a development convenience, not a production control.
  8. The database migration is incomplete. The current engine is SQLite even when compose provides PostgreSQL.
  9. No independent review. The repository contains no external audit report; the cryptographic primitives are standard, but the implementation has not been third-party assessed.

Reproduce the Docker path

The compose file starts the API and a PostgreSQL service, but the current engine is SQLite. The server also ships development TLS material and a sample JWT secret; replace them before exposing the service. 

docker compose up -d --build
# open https://localhost
# first boot prints the 12-word phrase once
# after a restart, unseal explicitly:
curl -k -X POST https://localhost/api/system/unseal \
  -H "Content-Type: application/json" \
  -d '{"phrase":"<your 12 words>"}'

Inspect the sealed state

GET  /health
GET  /api/system/status      # {"sealed": true}
POST /api/system/unseal      # {"phrase": "..."}
# every other route returns 423 while sealed

What this evidence proves

  • The seal, encryption, TOTP, RBAC, quorum export, audit, and extension paths exist in code and are connected to the data model.
  • The vault genuinely fails closed on restart: the key is not persisted, and the middleware returns 423.
  • The export path requires a calculated majority of admin PINs and encrypts the result with a one-time password.

What it does not prove

  • That the cryptographic implementation has been independently reviewed or side-channel tested.
  • That the deployment is highly available, multi-node, or backed by PostgreSQL at runtime.
  • That the extension’s injection is safe against a hostile page script after the value enters the DOM.
  • That the admin approval UI is complete; the reviewed build exposes the link without a render route.

11

Summary

LinkPass makes the root of trust explicit. The vault is sealed by default, the key lives only in memory, and the highest-risk operation requires a majority of admins.

The costs are real: someone must hold the phrase, a restart is downtime until unseal, and the quorum protects the application path rather than a hostile host administrator. The build is strongest where the design is most opinionated — the seal, the derivation, the one-shot extension payload, and the export threshold.

It is also honest about what is unfinished: the PostgreSQL runtime, the admin approval screen, and independent review. The correct description is “implemented and documented”, not “certified”.
